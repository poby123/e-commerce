# ADR-0012 하이브리드 검색 (BM25 + 벡터, RRF)

- 상태: 채택, 구현 완료 (2026-10-07)
- 재현: `scripts/seed-products.sh` 후 `python3 search-eval/evaluate.py`

## 구조
```
검색어 ─┬─ BM25 (Nori)            → 후보 상위 100 ─┐
        └─ e5 임베딩("query: …") → kNN 상위 10 ───┴─ RRF: Σ 1/(60+순위) ─▶ 후보 집합에 facet·필터·정렬
상품   ─── e5 임베딩("passage: 이름 브랜드 카테고리 설명") → dense_vector(384, dot_product, HNSW)
```
`mode` 파라미터: `KEYWORD` / `SEMANTIC` / `HYBRID`(기본).

## 결정과 이유
| 결정 | 이유 |
|---|---|
| ES 엔진은 그대로, 벡터는 `dense_vector` + kNN | 엔진을 바꾸지 않고 기존 Nori 검색, facet, 무중단 재색인을 그대로 쓴다 |
| **임베딩은 search-service 안에서** ONNX로 계산 (multilingual-e5-small, int8 118MB) | 외부 API 비용이 없고 상품 데이터가 밖으로 나가지 않는다. ES 안에서 모델을 돌리는 기능은 유료 라이선스 대상이다 |
| **RRF는 애플리케이션 코드에서** | ES의 RRF retriever는 basic 라이선스에서 거부된다(`current license is non-compliant for [Reciprocal Rank Fusion (RRF)]`, 직접 확인). 수식이 한 줄이라 직접 구현해도 비용이 작다 |
| 점수가 아니라 **순위로** 합친다 | BM25 점수(상한 없음)와 코사인(0~1, e5는 0.75~0.9로 몰림)을 서로 보정할 필요가 없다 |
| e5 규칙(`query:`/`passage:` 접두어, mean pooling, L2 정규화)을 코드에 고정 | 빠뜨리면 품질이 눈에 띄게 떨어진다. 정규화했으므로 `dot_product`(= 코사인) 사용 |
| facet은 합쳐진 후보 집합 위에서, 다중 선택 규칙 유지 | 키워드 검색과 같은 화면 동작을 유지한다 |

## 평가 (상품 35개, 질의 21개)
질의 종류: 정확(상품을 이름으로) 5 · 의도(필요를 설명, 상품명 단어 없음) 12 · 없는 상품(카탈로그에 없음) 4.

### 모드 비교 (하한선 없음)
| 모드 | 정확 Recall@5 | 의도 Recall@5 | 의도 MRR@10 | 없는 상품 검색 결과 수 |
|---|---:|---:|---:|---:|
| KEYWORD | 1.00 | **0.00** (12개 모두 0건) | 0.00 | 0 |
| SEMANTIC | 0.93 | 0.69 | 0.62 | 10.0 |
| **HYBRID** | **1.00** | **0.69** | **0.62** | 10.0 |

정확 검색 품질은 유지하면서 의도 검색을 0에서 0.69로 올렸다. 시맨틱만 쓰면 정확 검색이 손해를 본다.

### 문제: 없는 상품도 10개가 나온다 → 유사도 하한선 실험
| min-similarity | 의도 Recall@5 | 없는 상품 결과 수 | 정확 |
|---|---:|---:|---:|
| 없음 | 0.69 | 10.0 | 1.00 |
| 0.80 | 0.65 | 6.0 | 1.00 |
| **0.82 (채택)** | **0.53** | **2.2** | 1.00 |
| 0.84 | 0.19 | 0.5 | 1.00 |
| 0.86 | 0.00 | 0.0 | 1.00 |

- 작은 모델은 "관련 있음"과 "관련 없음"의 유사도 차이가 좁다(예: "방이 건조해요" → 가습기 0.808, 키보드 0.792). 어떤 하한선도 한쪽을 희생한다.
- **0.82 채택**: 엉뚱한 결과를 10건에서 2.2건으로 줄이면서 의도 검색은 키워드(0)보다 크게 낫다(0.53). 이 값은 상품 기획의 트레이드오프라서 코드가 아니라 config-repo에 둔다.
- 지연: 하이브리드 p50 19ms(키워드 20ms). 질의 임베딩 비용이 작다.

### 한계 (정직하게)
- 평가셋이 작다(21개). 방향을 보는 용도이지 통계적 결론이 아니다. 실서비스라면 검색 로그로 평가셋을 만들고 클릭 기반 지표(CTR, 구매 전환)로 본다.
- 모델 개선이 다음 개선점이다. 더 큰 다국어 모델(e5-base/large, bge-m3)이나 상위 결과를 다시 정렬하는 cross-encoder는 하한선의 트레이드오프 자체를 완화할 수 있다. 같은 `search-eval`로 비교하면 된다.
- 하이브리드를 기본으로 하면 고유한 상품명 검색에도 비슷한 상품이 뒤에 따라붙는다(정확히 일치하는 상품은 1위 유지, 스모크 테스트로 확인).

## 운영
- 모델은 git에 넣지 않는다. Gradle `downloadEmbeddingModel`이 `models/`에 받고, compose가 마운트한다.
- ONNX Runtime은 Java 힙 밖에 메모리를 잡는다. search-service는 mem_limit 1280m, 힙 50%로 두었다(실측 약 840MB).
- 매핑에 벡터 필드를 추가한 배포는 6a의 무중단 재색인으로 교체했다(39건, 임베딩 포함 5.8초).
