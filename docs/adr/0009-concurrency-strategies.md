# ADR-0009 동시성: 재고 차감 방식 비교와 선착순 쿠폰

- 상태: 채택 (2026-10-07)
- 재현: `docker compose --profile app up -d` 후 `load-test/run.sh` (약 2분). 원본 결과: `load-test/results/2026-10-07-summary.md`

## 측정 조건
- Apple M3 Pro 노트북, Docker Desktop **CPU 3개 / 메모리 9.7GB**. 이 안에서 서비스 9개, MySQL, Redis, Kafka, Debezium, k6가 함께 돈다.
- k6는 compose 네트워크 안에서 서비스를 직접 호출한다(gateway 제외). 서비스당 HikariCP 커넥션 10개(기본값).
- 회차마다 워밍업(JIT, 커넥션 풀) 후 측정. 3회 반복의 중앙값. 정합성 지표는 3회 중 최악값.
- 절대값보다 **같은 환경에서의 상대 비교**로 읽어야 한다.

## A. 인기 상품 재고 차감 (재고 3,000, 요청 20,000, 동시 200)
| 방식 | rps | p50 | p95 | p99 | 판매 | 재고가 남았는데 거절 | 초과판매 |
|---|---:|---:|---:|---:|---:|---:|---|
| 조건부 UPDATE (`WHERE quantity >= 1`) | 3,489 | 36ms | 165ms | 315ms | 3,000 | 0 | 없음 |
| 비관적 락 (`SELECT … FOR UPDATE` → UPDATE) | 3,838 | 33ms | 153ms | 195ms | 3,000 | 0 | 없음 |
| 낙관적 락 (version + 재시도 30회) | 3,633 | 12ms | 294ms | 864ms | 3,000 | **116** | 없음 |
| Redis Lua 게이트 → 당첨자만 DB | **5,624** | **8ms** | 178ms | 270ms | 3,000 | 0 | 없음 |

**해석**
- 네 방식 모두 초과판매는 없다(`StockDecreaseStrategiesTest`도 같은 결론).
- **조건부 UPDATE와 비관적 락의 차이는 노이즈 수준이다.** 요청의 85%가 품절 이후에 들어오고, 둘 다 결국 같은 행 락에서 줄을 선다. 로컬 네트워크라 왕복 한 번 차이도 작다. "비관적 락은 느리다"를 이 데이터로 주장할 수 없다.
- **낙관적 락은 경합에 약하다.** 충돌이 나면 다시 읽고 다시 시도하므로 꼬리 지연이 가장 길고, 재시도 한도에 걸린 116명은 재고가 있는데도 거절됐다. 정합성 문제가 아니라 **공정성** 문제다. 경합이 드문 데이터(회원 정보 수정 등)에 맞다.
- **Redis 게이트**는 품절 이후 요청을 DB 없이 돌려보내서 처리량 1.6배, p50 1/4을 얻는다. 대신 Redis와 DB 두 곳의 재고를 맞춰야 하고(DB 쓰기가 실패하면 Redis에 되돌림), Redis 장애 시 대책이 필요하다.

**결정**
- Saga의 재고 예약은 **조건부 UPDATE를 유지**한다. 한 문장이라 read-modify-write 실수가 없고, 여러 상품 예약, 예약 기록, 복구와 한 트랜잭션으로 묶이며, 성능 차이가 의미 있지 않다.
- 수천 명이 몰리는 타임딜 상품에만 Redis 게이트를 붙이는 것을 확장 지점으로 남긴다(예약/복구까지 Redis와 맞추는 작업 필요).

## B. 선착순 쿠폰 (1,000장, 요청 10,000 = 사용자 7,000 + 재클릭 3,000, 동시 500)
| 방식 | rps | p50 | p95 | p99 | 당첨 | DB 저장 | 1인 1매 | DB 반영까지 |
|---|---:|---:|---:|---:|---:|---:|---|---:|
| DB (정책 행 조건부 UPDATE + INSERT) | 2,457 | 136ms | 617ms | 1,156ms | 1,000 | 1,000 | 지켜짐 | 즉시 |
| Redis Lua → Kafka → 컨슈머 저장 | **7,906** | **37ms** | **196ms** | **289ms** | 1,000 | 1,000 | 지켜짐 | 3초 |

**해석**
- DB 방식은 모든 요청이 **정책 한 행**의 락에서 줄을 선다(troubleshooting #2의 데드락을 피하느라 락을 먼저 잡게 한 결과이기도 하다). 처리량이 그 한 행에 묶인다.
- Redis 방식은 판정(`SISMEMBER`→`SCARD`→`SADD`)을 Lua 하나로 원자 처리해 경합 자체가 없다. 낙첨 9,000건은 DB에 닿지 않는다. 처리량 3.2배, p95 1/3.
- 대가는 **결과적 일관성**이다. 당첨 응답(202) 후 쿠폰함에 보이기까지 최대 3초가 걸렸다. 정책별로 Kafka 키를 같게 해 한 파티션에서 순서대로 저장하므로 저장 쪽 락 경합은 없다.

**장애 시나리오와 대책**
| 상황 | 대책 |
|---|---|
| Redis 당첨 후 Kafka 전송 실패 | 응답 전에 전송 확인(ack)을 기다리고, 실패하면 Redis에서 해당 사용자를 지워 자리를 되돌린다 |
| 컨슈머가 같은 메시지를 두 번 받음 | processed_messages + UNIQUE(policy_id, user_id) |
| Redis 데이터 유실(재시작) | DB가 기준이다: CHECK(issued ≤ total)로 초과 발급은 막힌다. 운영이라면 AOF를 켜고, 시작 시 DB에서 당첨자 집합을 다시 채운다(미구현) |
| 두 발급 경로 혼용 | 정책의 `first_come` 플래그로 경로를 하나로 강제(COUPON-006) |
